# 2026-03-27 — Maya 2024 MCP Fix, macOS Terminal, Full Rebuild & Deploy

## Summary
Fixed Maya 2024 MCP connectivity (Editor API fallback chain), enabled the terminal on macOS (cross-platform shell detection, subprocess pipe backend), suppressed pywinpty warnings on non-Windows platforms, rebuilt all 6 Maya versions (Windows + Mac, 2024/2025/2026), and deployed everything to mcaeditor.com.

---

## Part 1: Maya 2024 MCP Connectivity Fix

### Problem
Maya 2024's commandPort has three bugs preventing MCP tool calls:
1. `echoOutput` doesn't work on ports opened at startup (all responses empty)
2. `maya.cmds` operations inside the commandPort handler abort the connection (`WinError 10053`)
3. Closing/reopening ports during `executeDeferred` crashes Maya

Maya 2025/2026 were unaffected.

### Root Cause
The MCP server (`mcp_maya_server.py`) sends tool scripts to Maya via TCP commandPort (port 7002). On Maya 2024, any `maya.cmds` call inside the socket handler triggers a connection abort. An attempted fix (close/reopen commandPort in `plugin_main.py`) crashed Maya on startup.

### Solution: Editor API Fallback Chain
Added a 3-level fallback chain to `mcp_maya_server.py`:

1. **Editor API** (new) — Routes through the MCA Editor's JSON-RPC server (`editor_api_server.py`, ports 7003-7013), which uses the internal adapter (`exec()` on main thread). Completely immune to commandPort bugs. Results captured via temp file.
2. **Direct commandPort** (existing) — stdout-redirect wrapper to port 7002. Works on Maya 2025+.
3. **Deferred commandPort** (existing) — lightweight Python via port 7002, queues work via `executeDeferred()`, results via temp file. Maya 2024 fallback when editor isn't open.

### Changes

| Action | File | Description |
|--------|------|-------------|
| REVERT | `mca_maya/plugin_main.py` | Removed close/reopen commandPort pattern (caused crash), restored simple open |
| EDIT | `mca_core/mcp_maya_server.py` | Added Editor API client (inline, standalone), 3-level fallback chain, shared helpers |

### Key Design Decisions
- Editor API client is fully inlined in `mcp_maya_server.py` (zero `mca_core` imports, standalone requirement)
- `_call_editor_api()` returns None on failure (soft fallback) vs `mcp_editor_server.py` which raises
- Shared helpers `_make_result_file()`, `_build_result_suffix()`, `_poll_result_file()` reduce duplication
- Editor API `execute_in_dcc` is synchronous on main thread, so result file exists before API response returns
- PID staleness check on discovery file prevents connecting to dead editor processes

### Testing
- Maya 2024 + Editor open: Editor API path works
- Maya 2025/2026: Unaffected (direct commandPort succeeds first)
- Maya 2024 startup: No crash (reverted to simple port open)

## Part 2: macOS Terminal Support

### Problem
The integrated terminal didn't open at all on macOS Maya. Multiple issues:
1. `terminal_factory.py` had Windows-only platform checks blocking native terminal
2. `terminal_backend.py` used `CREATE_NO_WINDOW` unconditionally (Windows-only flag)
3. Shell detection was Windows-only (PowerShell/cmd)
4. pywinpty module-level import fired on all platforms, logging warnings

### Changes

| File | Change |
|------|--------|
| `terminal_factory.py` | Removed Windows-only platform check from `_try_native()` |
| `terminal_backend.py` | Cross-platform shell detection (zsh/bash/sh on macOS) |
| `terminal_backend.py` | Conditional `CREATE_NO_WINDOW` (Windows only) |
| `terminal_backend.py` | Guarded pywinpty import with `if platform.system() == "Windows"` |
| `terminal_backend.py` | Added early return in `_ensure_conpty()` for non-Windows |
| `terminal_backend.py` | Changed `_run_subprocess()` log to DEBUG on non-Windows (subprocess pipe is the normal backend there) |
